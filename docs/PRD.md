# FabricQC Lite V0.1 — 产品需求文档（PRD）

> 状态：开发中 · 适用场景：杭州面料生产工厂 · 版本：Lite V0.1
> 本文档由项目启动指令整理而成。凡标记 **【开发默认值】** 的数值均为可配置的占位参数，**不是**工厂正式验收标准，必须由工厂质量负责人确认后替换。

## 1. 产品目标

以"验布"为核心，构建一套可在工厂现场真实投入使用的质检管理系统：

- 质检员用**微信小程序**在验布机旁或人工验布台完成扫码、测量、记录疵点、拍照、提交。
- 主管在**微信小程序**中收到授权范围内的审核提醒，直接审核。
- 管理员 / 业务员 / 质检主管在 **PC 管理后台**维护面料、布卷、标准、员工、任务，查询完整质检历史。
- 架构为将来的订单管理、AI 识别、MCP、ERP 对接、质量分析预留扩展空间，但 V0.1 **不**开发这些功能。

## 2. 用户与角色

| 角色 | 代码 | 主要职责 | 主要终端 |
|---|---|---|---|
| 系统管理员 | `ADMIN` | 员工账号、微信绑定码、基础资料、系统设置 | PC |
| 质检员 | `INSPECTOR` | 执行验布、拍照、提交审核 | 小程序 |
| 质检主管 | `QC_SUPERVISOR` | 分配任务、审核质检记录（授权部门范围内） | 小程序 / PC |
| 质量经理 | `QUALITY_MANAGER` | 配置质量标准、跨部门审核、查询分析 | PC / 小程序 |
| 业务员 | `SALES` | 查询面料与质检结果（只读） | PC |

一个员工可以拥有多个角色；`QC_SUPERVISOR` 角色可限定部门范围。所有权限均在后端校验，客户端提交的角色或用户 ID 不作为权限依据。

## 3. 功能需求

### 3.1 账号与身份
1. 管理员在 PC 后台创建员工：员工编号、姓名、部门、岗位、角色、账号状态；可选设置 PC 登录用户名与密码。
2. 管理员为员工生成**一次性微信绑定码**：有效期有限【开发默认值：24 小时】、仅能使用一次、数据库只存哈希、错误次数上限【开发默认值：5 次】后作废、已绑定员工不能重复绑定、一个微信不能绑定多个员工。
3. 员工首次打开小程序：`wx.login` → 后端 `code2Session` 取得 OpenID → 未绑定则输入"员工编号 + 绑定码"完成绑定。
4. 以后打开小程序自动静默登录。
5. 会话：短期 Access Token（JWT）【开发默认值：15 分钟】+ 随机 Refresh Token【开发默认值：30 天】，刷新时轮换，检测旧令牌重放即撤销会话；支持退出、管理员强制下线、员工禁用后立即失效。
6. PC 后台使用独立的用户名 + 密码登录，密码 Argon2id 哈希，连续失败锁定【开发默认值：5 次锁 15 分钟】。

### 3.2 面料与布卷
1. 面料档案：货号、中文名、英文名、成分、门幅、可裁门幅、克重 GSM、织造结构、涂层类型、颜色 / 色号、客户、默认四分制标准、默认客户标准、默认检验模板。
2. 生产批次：面料、生产批号、缸号、色号。
3. 布卷：系统 UUID、卷号（唯一）、面料、批次、缸号、色号、标称长度、实际长度、检验状态、二维码。
4. 批量导入布卷（CSV），自动生成唯一二维码标识，支持打印二维码标签。
5. 二维码内容为 `{QR_BASE_URL}/r/{二维码标识}` 的 HTTPS 链接：小程序内扫码可识别；将来可在微信公众平台配置"扫普通链接二维码打开小程序"。
6. 预留订单关联：`customer_orders` / `customer_order_lines` 表和布卷的 `orderLineId` 字段，V0.1 不开发订单 UI。

### 3.3 验布（最高优先级）
1. 模式：`MACHINE` 验布机 / `MANUAL` 人工，两者共用标准、疵点记录和评分引擎。
2. 检验范围：`FULL` 整卷全检 / `PARTIAL` 部分检验 / `SAMPLING` 抽检。通过"检验区段"（起止米数）精确记录实际检验了哪些长度；**全检必须覆盖整卷长度，否则不允许提交为全检**。
3. 现场流程：登录 → 我的任务 → 扫码 → 选择/确认模式与范围 → 查看规格与检查清单 → 测量 → 疵点 → 拍照 → 查看自动评分 → 提交审核。
4. 疵点：类型（可配置）、长度、宽度、米位、幅宽方向位置、严重程度、扣分（引擎计算）、照片、备注。
5. 测量：门幅、有效门幅、克重、卷长及模板中的自定义项目；不同面料可绑定不同检验模板。
6. 检查清单：模板定义的目视检查项（合格 / 不合格 / 不适用 + 备注）。

### 3.4 质量评分
1. 独立的质量评分引擎（`packages/quality-engine`），纯函数、可单测，服务端与小程序共用（小程序仅作预览，服务端结果为准）。
2. 四分制：按疵点尺寸分档扣分、特殊疵点规则（如破洞、连续性疵点）、每线性单位封顶、累计扣分、按实际受检面积标准化（每 100 平方码或每 100 平方米）、阈值判定。
3. 客户标准：可设置标准化得分上限、单卷总分上限、疵点总数上限、禁止疵点、按类型限制数量、严重度一票否决、测量值上下限（绝对值或相对规格百分比）、要求整卷全检。
4. **四分制与客户标准分别判定，再形成综合结论**；任一不合格即综合不合格；缺少必要数据为"无法判定"。严重缺陷、客户硬性要求不会因四分制合格而被忽略。
5. 所有规则版本化：标准版本发布后不可修改，只能新建版本；检验开始时对所用标准版本、模板和规格做**快照**。
6. 种子数据中的四分制标准参照 ASTM D5430 常见口径，标记为 **【开发默认值】**，名称中带"开发默认"字样，工厂须确认后另行发布正式版本。

### 3.5 拍照
1. 现场拍照 / 相册选择、预览、按检查点分类、关联疵点。
2. 小程序直传对象存储（服务端签发短时效、限定对象键的上传 URL），服务端不中转图片。
3. 同时上传原图和客户端压缩的缩略图。
4. 上传失败可重试；本地记录待同步状态。
5. 模板规定的必拍检查点、每个疵点至少一张照片（疵点照片要求可在标准中配置【开发默认值：必须】）；提交前服务端校验所有照片已上传成功。

### 3.6 离线草稿
1. 小程序本地保存完整草稿，界面明确显示"本地已保存 / 待同步 / 已同步 / 同步失败"。
2. 未同步成功的数据不得显示为"已提交"。提交只在服务端确认后才显示成功。
3. 草稿同步使用乐观版本号；提交使用幂等键防止重复提交。

### 3.7 审核与提醒
1. 提交时服务端校验完整性、重新计算结果、锁定记录、保存修订快照、创建审核待办、写入通知 Outbox——**同一数据库事务**。
2. 审核人确定规则：任务指定审核人 → 质检员的直属主管 → 任务部门范围内的 `QC_SUPERVISOR` → 全局 `QUALITY_MANAGER`。
3. 异步任务（BullMQ）发送微信订阅消息：必须用户主动授权、使用实际获批模板、按授权次数发送；未授权或发送失败**不影响**质检数据和站内待办。
4. 主管决定：`APPROVE` 通过 / `RETURN` 退回修改 / `REJECT` 判定不合格。系统判定不合格却审核通过时必须填写理由，记为"让步接收"。
5. 审核结果通知质检员（站内 + 订阅消息）。退回后质检员修改并重新提交（修订号 +1）。
6. 已审核记录不可修改；需要复验时新建一条检验记录并关联上一条。
7. 预留企业微信通知适配器接口，V0.1 不实现。

### 3.8 PC 管理后台页面
登录、工作台、员工与微信绑定、面料（含客户）、批次与布卷、质量标准（含疵点类型、检验模板）、验布任务、质检记录查询（按卷号查完整历史）、审核中心、系统设置（部门、审计日志、系统信息）。

## 4. 非功能需求
- 部署目标：腾讯云轻量 4C4G 40GB 3Mbps 上海；全部容器合计内存上限约 2.5GB。
- 开发机 macOS Apple Silicon；生产 Linux amd64。
- 不硬编码 IP、密码、密钥；PostgreSQL 不暴露公网端口；HTTPS。
- 可迁移到工厂本地服务器：容器化、独立数据卷、存储抽象、备份恢复脚本。
- 审计：所有写操作记录操作人、时间、前后值。

## 5. 明确不在 V0.1 范围
AI 疵点识别、MCP Server 部署、订单管理 UI、ERP、财务/采购/库存、高级 BI、企业微信通知实现、多租户 SaaS。
